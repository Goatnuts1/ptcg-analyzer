### 2a. Root cause: `fetch_standard_pool.py`'s name dedup is order-fragile

`build_pool()` dedupes by bare card name, keeping whichever print is encountered
**first** while iterating `list_set_codes()` — the set-id order returned by upstream's
`sets/en.json`. That order is not a contract; nothing pins it to release order or
guarantees stability run-to-run as upstream adds sets. When two Standard-legal prints
share a bare name (`"Alakazam"`, `"Drilbur"`, evidently others), which one wins the
bare-name slot depends on upstream's current set-list ordering, not on anything this
repo controls.

Confirmed directly against the freshly-fetched pool:

- **`db.get("Alakazam")`** now resolves to `sv6-82` (attacks `Strange Hacking` /
  `Psychic`) — not the print `test_alakazam.py` was written against, which expects an
  attack named `"Powerful Hand"` that doesn't exist on this print. `next(...)` raises
  `StopIteration`.
- **Bare `"Drilbur"`** now resolves to `sv5-85` instead of the Pitch Black print
  (`pbl-46`) the `mega_excadrill`/`alakazam_deck` lines were built and tested against —
  `test_metagross_cri_drilbur_pbl.py` catches exactly this ("expected Pitch Black
  Drilbur (pbl-46), got sv5-85"). **`"Drilbur (TEF)"`, the suffixed print
  `test_dig_dig_dig.py` needs, isn't in the pool at all** under a clean fetch.
- `test_chienpao.py` / `test_clefairy.py` fail the same way (a `next(... atk.name ==
  ...)` lookup that no longer matches) — consistent with the same root cause, not
  individually re-verified card-by-card this session.

This is a data-pipeline bug, not a game-engine bug — `tests/test_determinism.py`
(same seed -> byte-identical game, *given* a fixed pool) is untouched and still an
honest invariant. What's broken is the **pool build's own reproducibility**: two clean
fetches of "the same" Standard format can silently hand the engine a different print
for a bare name. That directly contradicts the print-collision contract in `CLAUDE.md`
("the pool's bare entry is left alone") — the bare entry isn't supposed to move at all,
and today it does. **Not fixed this session** — diagnosis only, since a real fix
(pinning dedup to a stable, explicit tiebreak — e.g. prefer the print the pool already
had committed via `manual_cards.json`'s print-collision suffix convention, or sort sets
by a real chronological key instead of upstream's array order) deserves its own
session and its own tests, not a rushed patch inside a scan run that has no network
access to cross-check the fix against real print IDs.

### 2b. `starmie_toolbox` / `gardevoir_real`: one card looks fabricated, not just missing

`gardevoir_real`'s reliance on `"Telepathic Psychic Energy"` is **already self-documented**
in `decks.py` as unresolved, with a substitution noted inline — that's honest, pre-existing,
not new.

`starmie_toolbox` is different and more concerning. `decks.py` uses `"Staryu"` and
`"Mega Starmie ex"` with no substitution note, and `tests/test_greninja_line.py`'s
docstring names an exact ID — `"Mega Starmie ex (me3-21)... verified against
limitlesstcg.com this session"` (commit `948f8e9`, 2026-08-13). In today's clean fetch:

- `me3-21` does not exist (the `me3` set has 11 Standard-legal cards in this pool;
  `me3-21` isn't one of them).
- No card named `"Mega Starmie ex"` or bare `"Staryu"` exists anywhere in the 1,331-card
  pool.
- The real Starmie line that **does** exist is `"Misty's Staryu"` (`sv10-46`, Basic,
  Bubble Beam) evolving into `"Misty's Starmie"` (`sv10-47`, Stage 1, Abrupt Flash) —
  **no Mega variant**. Pulled directly from this session's own fetch, so this part is
  verified against the real data dump, not memory.

I can't tell from here whether `"Mega Starmie ex"` was a genuine print that existed on
2026-08-13 and has since been pulled/renamed upstream (unlikely — TCG prints don't get
un-published), or whether it was never real and the "verified against limitlesstcg.com"
claim in that commit's test docstring was false. Either way it needs a networked
session to resolve against the primary source before anyone trusts `starmie_toolbox`'s
numbers again. **Flagging, not fixing or deleting** — retiring a deck or rewriting it
around `Misty's Starmie` is a bigger call than an unverified, network-blocked scan run
should make unilaterally.

### 2c. Probabilistic near-misses (unconfirmed link to 2a)

`test_mega_excadrill_deck.py` (Kieran never fires in its 12 fixed seeds) and
`test_toucannon_deck.py` (Area Zero Underdepths' bench-shrink clause never fires in 40)
use fixed seeds against a deterministic engine, so a result change between "used to
pass" and "fails now" needs *something* about the inputs to have changed — most likely
the same pool-dedup fragility reshuffling which print backs some card in these lists,
shifting downstream RNG draws. Not traced to a specific card this session; noted as
probably-related rather than independently root-caused, since chasing it further
needs the same network access the rest of this section is blocked on.
