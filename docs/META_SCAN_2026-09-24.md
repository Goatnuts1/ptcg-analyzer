## 2. What this scan actually found: a live regression in the house deck's card data

`data/*.json` is a gitignored build artifact — every session regenerates it from
`src/fetch_standard_pool.py` (pinned to the `PokemonTCG/pokemon-tcg-data` GitHub dump) plus
`data/manual_cards.json`. Rebuilding it this session (needed to run `--futures` and the
test suite at all) turned up a real fidelity break: **`tests/test_metagross_cri_drilbur_pbl.py`
and `tests/test_dig_dig_dig.py` failed**, and so, critically, did **`tests/test_mega_excadrill_deck.py`
— the house deck's own smoke test.**

Root cause: the fetch script de-dupes same-named cards by "first set encountered in
upstream's set list wins, manual supplement entries are skipped if upstream already has the
name." `mega_excadrill`'s decklist deliberately plays bare `"Drilbur"` = the PBL-46 print
(Call for Family: search 2 Basics to Bench), pinned via `data/manual_cards.json` exactly
because CLAUDE.md's print-collision convention says so. Upstream's own set-list order
shifted since this pin was last verified, and now a **different** Standard-legal Drilbur
print — Temporal Forces' sv5-85, with an unrelated "Dig Dig Dig" Ability and no Call for
Family — wins the bare-name race first. The manual pin's "skip if name already seen" check
only compared by name, so it silently let the wrong print win. **In a freshly-rebuilt pool,
mega_excadrill's Drilbur was quietly playing the wrong card** — Call for Family (the card's
actual role in the list, per `decks.py`'s own comments) would never have fired.

**Fixed** (`src/fetch_standard_pool.py`, diff below): the manual-merge step now compares by
`abilities`+`attacks` content, not name or id. A same-named upstream card with an identical
moveset is still treated as a harmless republish (confirmed for `Mega Excadrill ex`,
`Mega Slowbro ex`, `Gwynn`, `Gladion's Final Battle` this session — same abilities/attacks,
cosmetic id/rules-text differences only, upstream correctly wins as designed). A same-named
upstream card with a **different** moveset is a genuine print collision: the manual pin now
keeps the bare name (matching what `decks.py`/`effects.py` already commit to) and upstream's
card is relocated to `"Name (SETCODE)"` instead of being silently discarded — which
incidentally also fixed `tests/test_dig_dig_dig.py` for free, since `"Drilbur (TEF)"` (the
name `effects.py`'s registry already expected) is now populated with real data straight from
the same upstream fetch, not fabricated.

Verified: `test_dig_dig_dig.py`, `test_metagross_cri_drilbur_pbl.py`, and
`test_mega_excadrill_deck.py` all pass green after the fix. `cli.py --futures` also
silently self-corrected — `mega_excadrill`'s rotation-risk score had drifted from 75.2 to
71.7 (a phantom +5pt rotation exposure from the wrong Drilbur print's regulation mark) and
is back to 75.2, matching the last known-good `docs/FUTURES_2026-08-21.txt` baseline exactly.

**A second, related regression was found but NOT fixed — flagged for next session:**
`Alakazam` has the same "upstream set-order shifted, wrong print now wins" problem, breaking
`tests/test_alakazam.py`, `tests/test_chienpao.py`, `tests/test_clefairy.py`. Unlike
Drilbur, there is **no manual pin to fall back on** — the MEG print (`decks.py`'s
`alakazam_deck`, "Psychic Draw" Ability / "Powerful Hand" attack) was apparently always
sourced live from upstream and never needed a manual entry, until a second Standard-legal
Alakazam print (`sv6-82`, plain "Strange Hacking"/"Psychic") started winning the dedup race
instead. I have partial card text for the MEG print from the test's own docstring
(Ability/attack text only — no HP, weakness, retreat cost, or set id), which is not enough
to write a real `manual_cards.json` entry without fabricating fields, and web verification
is blocked this session. **This one needs a primary-source check next scan**, not a repo fix
today.

## 7. What changed for `mega_excadrill`

**A real one, this week: the house deck's Drilbur was silently playing the wrong print in
any freshly-rebuilt environment, until the fix in §2.** This wouldn't have been visible from
the matrix numbers (those were measured against a correct pool at the time) — it would only
have bitten a new session or CI run regenerating the pool from scratch, exactly the kind of
failure `CLAUDE.md`'s "Deterministic — a tested invariant" section doesn't cover (that
invariant is about same-seed reproducibility within one build, not stability of the build
itself across upstream data changes). No live-meta drift to report otherwise; no new bad
matchups surfaced (no fresh matrix run this week). `Alakazam` carries the same class of bug,
unfixed — if you're piloting into an Alakazam Dudunsparce opponent, that's not this deck, so
no direct action, but it's the next thing this scan should check once the fix pattern from
§2 can be replicated with real card data.
