## Engineering housekeeping found and fixed before anything else ran

Two pre-existing problems blocked this scan from even starting and are fixed in this PR:

1. **`cli.py` was completely broken** (`--list`, the default no-args usage, and `--futures`
   all crashed with `UnboundLocalError: cannot access local variable 'DECKS'`). Cause: the
   `--futures` branch added in the `f9b7a07` futures commit did a redundant
   `from src.engine.decks import DECKS` *inside* `main()`, which is already imported at
   module scope (`cli.py:26`). Python's scoping rules make any name assigned anywhere in a
   function local to the *whole* function, so that one extra import line shadowed the
   module-level `DECKS` for every other branch in `main()`, not just `--futures`. This has
   been broken since that commit landed — it did not regress this week, it was just never
   exercised by a scan run with `--list`/`--futures` until now. Fixed by deleting the
   redundant local import (`cli.py`); `DECKS` now resolves to the module-level import
   everywhere in `main()`.
2. **`data/standard_pool.json` doesn't exist until you fetch it.** It's gitignored by
   design (a reproducible build artifact, see `src/fetch_standard_pool.py`'s docstring),
   but a fresh session has no pool on disk at all. Ran
   `python3 src/fetch_standard_pool.py` and moved the output into `data/` — 1,331
   Standard-legal cards. **Not committed** (same as every other session — regenerate it the
   same way next time).

### A real data-integrity finding from that rebuild — not fixed this scan, flagged instead

Running the full suite after rebuilding the pool (102 `tests/test_*.py` files run as
scripts) surfaced **18 pre-existing failures**, independent of anything in this PR:

- `test_arena.py`, `test_train.py` — missing `torch`/`numpy` in this environment. Unrelated
  to card data; the learning-engine pieces, not the sim.
- `test_metagross_cri_drilbur_pbl.py` — **the print-collision dedup picked a different
  print of bare `"Drilbur"` than the test expects** (`sv5-85` Temporal Forces instead of
  `pbl-46` Pitch Black). Root cause: `fetch_standard_pool.py`'s de-dupe-by-name keeps
  whichever print it sees *first*, in the order upstream's `sets/en.json` lists set codes —
  an order this project doesn't control and apparently isn't stable release-to-release.
  This is a real reproducibility gap in the print-collision design CLAUDE.md documents as
  deliberate: it assumes a stable "first print wins" order that the live upstream dump does
  not actually guarantee.
- `test_dig_dig_dig.py`, `test_gardevoir_real_deck.py`, `test_gardevoir_real_line.py`,
  `test_hide_n_sneak_deck.py`, `test_ismcts.py`, `test_mcts_keys.py`,
  `test_slowking_ogerpon_trainers.py`, `test_starmie.py`, `test_starmie_support.py`,
  `test_greninja_line.py` — reference cards (`Telepathic Psychic Energy`, `Mega Starmie ex`,
  bare `Staryu`, `Drilbur (TEF)`) that are in **neither** the live upstream dump **nor**
  `data/manual_cards.json`. `Staryu` specifically now resolves to `"Misty's Staryu"`
  upstream — a name collision, not an absence.
- `test_alakazam.py`, `test_chienpao.py`, `test_clefairy.py` — a hardcoded attack-index
  lookup (`next(i for i, atk in enumerate(...))`) raises `StopIteration`, consistent with an
  upstream print swap changing which attacks a resolved card has.
- `test_mega_excadrill_deck.py`, `test_toucannon_deck.py` — "didn't fire in N seeded games"
  assertions came back empty; could be the same print drift or could be seed-sensitive
  flake — not disentangled this scan.

**Why this isn't fixed here:** none of it is this scan's job (live-meta coverage/builds),
all of it predates this week, and guessing at fixes for cards I can't verify real text for
would violate the "real card text only" rule. **Why it matters anyway:** the core engine and
`tests/test_determinism.py` are unaffected (verified: `mega_excadrill` vs `dragapult` plays
cleanly under greedy, determinism invariant holds), so this is NOT an engine-correctness
regression. But it is evidence that **the pool is not actually pinned/reproducible** the way
CLAUDE.md implies — a second data-integrity finding beyond the print-collision one above.
Recommend a follow-up: either vendor a pinned snapshot of the upstream dump, or make the
dedupe order explicit (e.g. prefer the newest set by release date) instead of "whatever
order upstream's set list happens to be in this week."
